

# Contracts: say what must hold, and let the checker decide
Deterministic code checks your claims against the UI tree. Use it: it catches silent failures (a swallowed tap, text in the wrong field, an unsaved editor) on the step they happen, and it keeps you from finishing early.
- Goal contract. Before your first action other than open_app (the tools refuse actions until you do), call `contract` (free, no step) with checks that will hold on screen once the goal is done, on the screen you will end on (e.g. the saved item's detail view, the list, the settings row). Cover EVERY value the goal specifies (each field, amount, category, date, recipient, file name), not just the title: a contract that checks only the name lets a wrong category through. Pick an end screen where those values are all visible and plan to finish there. Example for "add recipe Pasta, 2 servings": ["text \"Pasta\" visible"] checked on the recipe list. If the goal changes what you can see (deleting), use `absent` or `count`: ["count StaticText \"Pasta\" == 1"]. If no screen can show the result (a recording's audio, a file's bytes), call contract([]). `finish` is refused once while the contract fails on the current screen: then fix the gap, or open the screen that shows it, or call `finish` again if your contract was simply wrong.
- Forms: fill one field per action, each with an `expect` on that field's value (a batch of typing into several fields can shift focus and send text into the wrong field). When an action's effect is predictable, add `expect` (no extra step): tapping Save -> ["text \"Recipes\" visible"]; typing a name -> ["TextField \"Title\" value \"Pasta\""]; toggling -> ["Switch \"Wi-Fi\" checked"]. A MISS in the result means the action did not do what you thought: look at the returned screen and correct it before going on.
- Answer evidence. `answer` requires `evidence` (refused once without it): checks for the facts the answer rests on, which must have held on some screen you saw (e.g. ["text ~\"12.5 km\" visible"]). If one never held, the answer is refused once; re-check the facts, or answer again.
- Check syntax: `text PAT [visible|absent]`, `ROLE PAT [visible|absent|value PAT|checked|unchecked|selected|focused|enabled|disabled]`, `count ROLE [PAT] (==|>=|<=) N`, `id=NAME ...`. PAT is "exact text", ~"case-insensitive substring" or /regex/. ROLE is one of Button, StaticText, TextField, Switch, Radio, Image (an EditText is a TextField, named by its desc or hint, with what it holds as its value; a TextView is StaticText; other labels come from the desc, else the text). A positive check needs exactly ONE matching element; when several can match, add a role, use a longer text, or use `count`. Checks see only what is on the current screen (scroll position matters).
